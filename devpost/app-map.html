One useful code route: a search request meets the security boundary

Follow one “Search” click from the network edge to the paid provider. Each stop answers: what may this request do, and how much may it cost?

Stop 1 — reject bad input before anything else

Open server/index.ts, find app.use('/api',express.json({limit:'32kb' and then app.post('/api/searches'. The body is capped at 32 KB, a cross-site Origin is refused, and z.strictObject({preferences:PreferencesSchema,…}).parse(req.body) rejects unknown or oversized fields. Only after that does requireOwnerCookie check the anonymous browser identity.

Stop 2 — rate limits and spending caps before any provider call

Open server/store.ts, find reserveRun (no practical per-user cap for private demo use; only a runaway-loop stop) and reserveModel (per-model Groq free-tier allowance, falling over from gpt-oss-120b to gpt-oss-20b) and reserveAgent ($1.50 and 8 Agent runs per UTC day). These run inside one serialized transaction, so two simultaneous clicks cannot both squeeze under a limit. server/agent.ts → walletAllowsAgent adds a third gate: no run if wallet auto-reload is on or the balance is low, so a top-up can never be triggered.

Stop 3 — untrusted output is validated too, and the tests prove the “no” paths

Model and Agent output are also input. server/model-contract.ts → salvage removes only the smallest invalid item (one fact, lead or opportunity) instead of trusting or losing the whole page. Then open tests/usage-store.test.ts (“caps daily spend”) and tests/agent.test.ts (“refuses when wallet auto-reload is on …”). Both assert that the forbidden action did not happen: no reservation, no run created.

Trust and data boundaries

  • Browser: reactions, selections, academic details, answers, availability and completion history. Reset requires confirmation. Browser storage is not a private server account or an encrypted vault.
  • Server: anonymous ownership, bounded public quotes/cache and operational quotas. Private local files support one process, not scaled replicas. Expired question ownership does not erase browser answers.
  • TinyFish: public search and page requests. No personal profile or answer text. The paid Agent is opt-in (TINYFISH_AGENT_FALLBACK=on) and is used only after Fetch fails, only on likely-official hosts, capped per run and per day, with a wallet check and no top-ups. It is told never to sign in, apply or submit forms. Its text goes through the same quote/ownership checks and is labelled “Read by TinyFish Agent”.
  • Groq: public interpretation and consented answer/rubric scoring using the learner’s native configuration. It receives only the schema structure (value rules are described in text) because its strict mode rejects a whole page for one bad value; the strict local schema still decides what is accepted, dropping only the smallest invalid item. No code execution or provider/tool action is granted to model output.
  • Secrets: runtime server environment only. Neither API keys nor session secret belong in source or this guide.
  • Output: quoted evidence is preliminary. Unknown funding, grades, requirements and selection stages stay unknown. A short foundation score is not proof of practical competence.

How the behavior is checked

tests/planning.test.ts uses fixed clocks for grade/year changes, shared hours, cutoff timing, exams, external waiting, closed/ineligible goals, date-only conservatism, DST and completion/reopen. Shared tasks are allocated once, and weeks cannot exceed capacity.

scripts/browser-planning.ts uses declared API fixtures to exercise the actual UI, failures/retry, consent, both tracks and restoration at phone/tablet/desktop widths. Fixtures are tests, not live evidence or app demo data.

scripts/browser-live-planning.mjs exercises native TinyFish/Groq through the public app. Its complete end-to-end result is still pending the remaining provider allowance. Mechanical checks do not substitute for this check or for the learner’s final hands-on review.

A practice to reuse

Put the gate before the cost, then test the “no”. “Don’t overspend” is vague. Here it is concrete: validate input, reserve against a limit in one atomic step, and only then call the paid service. Tests prove the provider was not called when a gate said no. Reuse it anywhere an endpoint triggers an AI, email or payment call: write down the unacceptable action, put validation and a quota before it, and assert it did not happen.
